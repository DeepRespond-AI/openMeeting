# 单服务镜像更新流程

适用于本机构建镜像，再上传到 Linux 服务器的离线部署。以下以 `user_ms` 为例；其他服务替换为实际服务名。完整部署包的生成和首次部署见[根目录 README](../README.md#服务端离线打包与部署)，备份和恢复要求见[服务端运维](../server/OPERATIONS.md)。

## 更新步骤

1. **修改本地代码并测试**：完成相关单元、接口和必要的真实流程验证，明确受影响的服务。
2. **在本机构建新镜像**：只构建需要更新的服务，其余服务无需重新构建。在仓库根目录执行 `docker compose -f server/docker-compose.yml build user_ms`；构建失败则停止，不导出旧镜像作为新版本。为成功构建的镜像标记本次发布的独立标签。
3. **导出、压缩并上传镜像**：通过 `docker image save` 导出本次镜像，产物放在 `.artifacts/`；将压缩包及校验值上传服务器，核对文件完整性。镜像不包含数据库、录音、模型和数据卷。
4. **服务器导入新镜像**：使用 `docker load -i <镜像归档>` 导入。若压缩包里包含一个 `user-ms.tar` 文件，先解压再导入该文件；此时运行中的旧容器不变。
5. **备份并更新部署配置**：保存当前 Compose、服务器 `.env`、数据库备份和旧镜像标签，再把部署配置中的 `user_ms.image` 改为新标签。新增环境变量时，同时补充 `user_ms.environment` 映射并设置服务器 `.env`。外部域名、证书等依赖应先验证就绪。
6. **替换单个服务容器**：在服务器部署目录执行下面的命令。Compose 自动停止、移除旧 `user_ms` 容器，用新镜像创建并启动容器，重新挂载原有数据卷；其余服务不随之重建。
7. **验证业务结果**：检查健康状态、鉴权及本次改动的成功和关键失败路径。例如更新安装包下载功能时，验证真实下载、文件大小与哈希，确认 Windows 等已有平台仍可正常下载，并核对业务数据未丢失。

```bash
docker compose --env-file .env -f docker-compose.offline.json config --quiet # 检查部署配置
docker compose --env-file .env -f docker-compose.offline.json up -d --no-deps --no-build --pull never user_ms # 只替换 user_ms，保留数据卷
docker compose --env-file .env -f docker-compose.offline.json ps -a # 查看服务状态
docker compose --env-file .env -f docker-compose.offline.json logs --tail 100 user_ms # 查看启动、迁移和业务日志
```

`--no-deps` 适用于依赖服务已经运行且不需要更新的情况；如果修改涉及多个服务或依赖关系，按实际影响范围一起发布。

## 镜像、容器与数据的区别

| 资源 | 更新时的变化 |
|---|---|
| 新镜像 | 导入服务器，供新容器使用 |
| 旧容器 | 被 Compose 停止并移除 |
| 新容器 | 使用新镜像和当前服务器配置创建 |
| 数据库与数据卷 | 继续使用，不因容器重建而删除 |
| 旧镜像和配置备份 | 验证完成前保留，用于评估和执行回退 |

无需先执行 `down`，也不要通过 `down -v` 更新服务。服务启动时可能执行镜像内的数据库迁移；存在结构变更时，先评估兼容性，单纯换回旧镜像不一定能恢复旧版本。

## 验证后的清理

确认运行正常并满足回退保留要求后，可清理已导入的镜像传输文件和明确不再需要的旧镜像、配置及数据库备份。先检查旧镜像没有被任何运行或停止的容器引用。旧数据库备份是导出的文件，不是运行中的数据库；清理备份不删除业务库或数据卷。

Docker 镜像显示的大小包含共享层，新旧镜像的大小不能直接相加作为新增磁盘占用。用 `docker system df -v` 查看共享与独有占用；传输用的 `.tar` 和压缩包则额外占用服务器磁盘。
