# 多人会议聊天与文件：统一使用 IM


## 当前实现

会议房间继续由 `meeting_ms` 管理，音视频继续使用已有 RTC 频道。会议内聊天由同一深应智联 IM 服务的**私有群**承载，附件由 IM **群文件**承载。没有新建本地消息归档、文件存储、消息重传或离线队列；IM SDK 自身的缓存、队列和历史能力继续使用。

```text
LiveRoom
  ├─ room.id → RTC channel_id（既有音视频）
  └─ im_group_id → IM 私有群
                     ├─ IM 消息、历史分页、已读和重连恢复
                     └─ IM group_file 上传、对象存储、鉴权下载
```

- 后端在普通入会、幂等重入及等候室批准时准备群成员授权，持有房间锁并在成员入会广播前完成；未获准的等候室成员不加入群。IM 暂不可用仍保留业务房间，`chat-session` 继续承担显式失败及幂等恢复。
- 已获准入会的两端在入会后立即调用 `POST /api/v1/rooms/{id}/chat-session`，获得 `{transport:"dr-im-group", groupId}`，刷新会话并建立消息订阅。移动端由 App 持有 `roomChatLifecycleProvider`，关闭弹层及最小化会议不释放；桌面由 RoomProvider 持有。只有离会/结束时释放，重入重新建立。打开聊天仅展示已同步消息并更新可见/已读状态。未登录、未入会、等待室成员及已结束房间不能获取授权。
- `meeting_ms` 持有房间行锁，通过 `gateway_ms` 的内部鉴权 RPC 调用 `user_ms` 的服务端 IM SDK，创建/找回群并直接添加当前成员。首次创建的群 ID 保存于 `live_rooms.im_group_id`；每个业务房间至多一个绑定，不使用六位会议号作为群 ID。
- 群主是后端专用 IM 账号 `openmeeting-meetings`，客户端参会者均为普通成员，`member_invite=disabled`。会议主持人角色不授予 IM 群主/管理员权限；主持人转让不会让客户端绕过会议权限修改群。
- 客户端使用现有 `IMContext` 登录态，调用 `conversations.refresh`、`messages.open/send`，订阅 SDK 消息列表，使用 `loadOlder` 翻页。真实模式不接收业务 WS 的聊天消息，不调用旧聊天 REST/IPC。
- 文件使用 `files.upload(file, {purpose:"group_file", group_id, kind:"file"})`。IM 返回固定文件地址后发送 IM 文件消息；上传进度、取消、平台错误直接反馈给用户。下载由 `desktop.download(fixedFileUrl)` 完成，SDK 换取下载地址并原生写盘；不经过业务后端、不把完整文件复制成 Rust IPC 数组。
- 显式离会、主持人移出、成员超时清退，会先撤销 IM 群成员资格。平台拒绝或不可用时明确报错/等待下一次扫描，不把“业务删除成功但 IM 仍可访问”静默当作成功。
- 结束会议先调用幂等 `groups.delete(reason="Meeting ended")` 解散会议专属 IM 群，再提交业务结束和会后录音任务；失败返回 503，房间保持活动以便重试。前端取消上传与订阅、清空消息/引用/未读，并隐藏该场会话；消息工作台不展示已解散会话。每场新会议绑定自己的群，聊天仅在会议存续期间使用。平台数据保留及成员延迟移除遵循 IM 策略，不代表立即物理擦除。
- 会议聊天使用跟随系统主题的左右消息气泡、连续发送者分组、时间与发送状态；回复、转发、反馈与撤回位于消息操作弹层。成员变动 `tip` 不作为聊天消息卡片展示。图片、视频和音频通过鉴权原生缓存预览（最多 30 MB）；普通文件中可识别的媒体格式也支持预览，`.txt/.md/.csv/.json/.log` 以转义纯文本展示（最多 1 MB）。其他格式提示下载打开；关闭/卸载预览释放缓存。
- IM 请求设置截止时间且禁用 SDK 自动重试，避免业务 RPC 超时后继续后台重试授予成员资格。IM 建群结果丢失时，按群属性 `openmeeting_room_id` 找回，不直接重复建群。跨服务事务仍不具备原子提交，见下面的缺口。

会中聊天和文件在 IM 服务中管理；业务会议数据库负责房间身份与授权。

## 为什么没有直接使用 IM Chatroom 模块

用户要求聊天室和聊天文件统一使用自己的 IM 服务；本实现不把 IM 能力缺失改造成另一套本地聊天系统。现有 IM Chatroom 模块的公开接口目前无法同时满足私密会议和完整历史需求，所以选择同一服务现有的私有群能力。

| IM 能力问题 | 当前规则/影响 | 建议在 IM 服务侧补齐 |
|---|---|---|
| Chatroom 没有入房票据、成员 ACL 或进入前同步回调 | `listed=false` 只隐藏列表；知道 ID 的应用用户仍可能进入，不能代替密码和等候室鉴权 | 复用 RTC 风格短期入场票据，绑定用户/业务房间，支持撤销、踢出及断线恢复后的重验 |
| Chatroom 没有完整历史分页 | 最近消息默认 50 条、最多 200 条，只保存 24 小时；封禁/解散清空，离线消息不补发 | IM 原生历史归档、游标分页、保留策略及会后只读查询；业务侧不另造消息库 |
| 缺少聊天室作用域的文件用途 | `attachment` 允许应用内持有地址的任意登录用户换取下载链接，默认 30 天过期；没有 `chatroom_file` | 聊天室/业务成员作用域的文件 ACL、入场票据鉴权、会后归档权限与独立保留策略 |
| Chatroom 在线消息会限流/丢弃且不保证完整送达和跨用户顺序 | 不能把最近消息当作可靠会议记录 | 若作为正式会议记录承载，应提供可靠消息模式和断线补齐能力 |
| 群/聊天室创建缺少业务幂等键和按业务键查询 | IM 生成 ID，创建响应丢失后要枚举属性找回；服务账号群量增加会影响恢复效率并触及用户群数量配额 | `external_id`/幂等创建键、按业务键查询、服务账号配额与批量生命周期接口 |
| 缺少明确的“归档只读”生命周期 | 当前结束会议会解散专属群，不提供会后只读聊天入口 | 归档状态：禁止新消息/上传，保留成员查询、消息历史和文件下载，并定义历史参会者权限 |
| 群文件上传与文件消息发送分为两步 | 上传成功、发消息失败时群文件仍存在；重选文件可能重复上传 | SDK 的群文件消息发送任务：复用上传结果、进度、取消、持久重试及失败处理 |
| IM 侧授权与业务事务无法原子提交 | 应用通过行锁、明确失败和重试降低窗口；网络响应不确定时仍需平台幂等/撤销能力支撑 | 幂等成员授权/撤销、可查询操作结果，必要时平台票据强绑定业务会话 |

以上是文档/接口限制和集成改进项，不把尚未进行真实平台验证的假设写成服务故障。

## 配置与上线边界

沿用现有 IM 应用、服务端凭据、客户端 SDK 和引擎配置。IM 应用必须启用私有群、消息和群文件服务，文件存储额度及群配额足够；按业务要求配置消息保留期限、`group_file_enabled` 和 `group_file_retention_days`。不新增 App Secret 客户端配置。

后端负责会议群绑定与授权；客户端通过 `room_chat_session` 获得会话入口。平台凭据保留在服务端。
