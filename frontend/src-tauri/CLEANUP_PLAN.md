# Src-Tauri 代码清理计划

> 文档类型：开发过程或验收记录。保留当时的设计、环境和执行边界；当前能力以[功能状态](../../docs/feature-status.md)为准，不作为当前启动或升级指南。

## 分析摘要
对 src-tauri 代码的分析发现，多个部分需要清理和优化。快速开发积累了一些架构债务，可按阶段系统处理。

## 主要问题

### 1. **历史代码残留**
- **`lib_old_complex.rs`**（2,437 行）：大型历史文件，似乎包含旧实现。
- **两套音频系统并存**：同时存在 `audio/` 和 `audio_v2/` 模块，表明迁移尚在进行。
- 多处 `pub use *` 通配导出导致依赖边界不清。

### 2. **尚未完成的实现**
- audio_v2 各模块中有 **20 多处 TODO 注释**，对应未完成功能。
- audio_v2 系统存在大量占位代码，阶段 2、3、4 尚待实现。
- 调试输出散落在各处，共有 9 处 println!/dbg!。

### 3. **模块组织问题**
- **模块结构重复**：多个模块采用相同结构，mod.rs 中只有一条 pub use *。
- 两套音频系统之间的**边界不清**。
- 多个模块存在**命令及处理器重复**。

### 4. **依赖管理**
- **Cargo.toml 共 122 行**，部分依赖可能未使用。
- 某些 Git 依赖可以改为稳定发行版本。
- 硬件加速特性开关较复杂，当时处于关闭状态。

## 分阶段清理计划

### 阶段 1：移除无效代码和旧系统
**优先级：高 | 风险：低 | 预计：2–3 小时**

1. **移除历史文件**
   - 确认无现行依赖后删除 `lib_old_complex.rs`。
   - 更新其余引用。

2. **整合音频系统**
   - 评估 audio_v2 的完成情况。
   - 完成 audio_v2 迁移，或移除未完成模块。
   - 保持单一、清晰的音频系统架构。

3. **清理 TODO 标记**
   - 处理或记录 20 多处 TODO/FIXME 注释。
   - 移除不再计划完成的占位实现。
   - 将其余 TODO 纳入正式问题跟踪。

### 阶段 2：重构模块组织
**优先级：中 | 风险：中 | 预计：4–5 小时**

1. **简化模块结构**
   - 移除只含一条 pub use 的冗余 mod.rs 文件。
   - 将相关功能整合到数量更少、内聚性更高的模块中。
   - 明确模块边界及职责。

2. **统一命令模式**
   - 各模块采用一致的命令及处理器模式。
   - 减少跨模块命令重复。
   - 在适用位置实现共享命令 trait。

3. **改进导入及导出**
   - 尽可能将 `pub use *` 改为明确导入。
   - 为各模块定义清晰的公开 API。
   - 移除未使用导入及无效代码标记。

### 阶段 3：优化依赖和配置
**优先级：中 | 风险：低 | 预计：2–3 小时**

1. **依赖审查**
   - 审查 40 多个依赖的实际使用情况。
   - 尽可能将 Git 依赖改为稳定 crate 版本。
   - 移除未使用依赖。
   - 合并重复依赖。

2. **优化特性开关**
   - 重新启用并测试硬件加速特性。
   - 设置合理的默认特性组合。
   - 记录特性开关用法及平台要求。

3. **清理配置**
   - 统一各模块的配置模式。
   - 集中维护共享配置逻辑。
   - 统一错误处理方式。

### 阶段 4：改进代码质量
**优先级：低 | 风险：低 | 预计：3–4 小时**

1. **统一错误处理**
   - 将容易触发 panic 的写法改为明确的错误处理。
   - 各模块使用一致的错误类型。
   - 改进错误消息及日志。

2. **性能优化**
   - 审查超过 1000 行的大文件，寻找拆分机会。
   - 优化 async/await 使用方式。
   - 减少高频路径的内存分配。

3. **文档与测试**
   - 增加模块级文档。
   - 记录公开 API。
   - 考虑为关键路径增加集成测试。

## 风险评估
- **低风险**：依赖清理、文档及 TODO 清理。
- **中风险**：模块重组及音频系统整合。
- **高风险**：当时未识别到；多数修改为增量变更或边界明确的独立修改。

## 成功指标
- 总代码行数减少 15–20%。
- 清除所有 TODO/FIXME 注释。
- 缩短编译时间。
- 降低模块复杂度，提高可维护性。
- 保持所有既有功能完整。

## 建议执行顺序
1. 从阶段 1（移除无效代码）开始，修改风险最低。
2. 继续阶段 3（依赖），不依赖代码结构调整。
3. 执行阶段 2（重构），需要最谨慎地评估。
4. 最后完成阶段 4（质量改进）。

本计划旨在保留全部既有功能的同时，提高代码可维护性。
