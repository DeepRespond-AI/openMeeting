# 部署规格与容量验收

服务端参考目标为 Linux x86_64、Python 3.11 和 PostgreSQL 16。meeting_ms 使用进程内房间状态，当前按单实例部署；不能直接通过增加副本扩大会议信令容量。客户端 RTC 媒体由所接平台承载，业务 HTTP 的吞吐不能替代平台容量或真实会议测量。

## 运行模式

| 模式 | 配置 | 资源与能力边界 |
|---|---|---|
| 基础开发 / 云端推理 | `OPENMEETING_STT_RUNTIME=stt-cloud` | 不安装本地 Torch、Whisper、FunASR；可完成管理端、账号、数据与安装包流程。转写/总结需配置实际服务，不保证无账号完成全部功能 |
| 本地 CPU 推理 | `OPENMEETING_STT_RUNTIME=stt-cpu` | 安装锁定的 CPU 引擎；额外预留模型、音频、队列和推理内存。并发先保持 1，按选定模型实测 |
| NVIDIA GPU 推理 | GPU Compose 覆盖 | CUDA 12.4 / cuDNN 9、匹配的 Torch 与驱动；需在真实 GPU 上确认模型、显存与并发，CPU 测试不代表此模式通过 |

模式改变属于镜像依赖变化，需要重新构建 stt_ms；其他 `.env` 运行配置按相同 Compose 组合重新 `up -d`。已有卷和模型缓存保留。镜像共用 `server/uv.lock`，CPU/CUDA extras 互斥，不能通过临时 `pip install` 让生产容器偏离锁文件。

## 建立自己的规格基线

目前不承诺统一的最低内存或最大会议人数。部署 E2E 会记录 Docker 可用 CPU、内存、架构、构建与启动耗时，以及本地健康接口的延迟，作为当前环境的启动基线；它不是会议容量基准。

2026-11-06 的隔离验收使用 Docker Linux x86_64、12 个 CPU、约 15.5 GiB 可用内存，以及 `stt-cloud` 模式：首次 local 存储构建及启动耗时 888 秒（包含联网拉取），缓存构建的 MinIO 运行耗时 21 秒。MinIO 路径下载并验证了约 46.8 MiB 的 Windows x64 NSIS 调试安装包；本机健康接口 20 次采样，中位数 1 ms、P95 2 ms。这些数值只描述该次构建、启动和下载环境，不代表最低配置、模型速度或最大会议人数。复现方式见[发布验收](releases.md#本地部署-e2e)。

同轮还独立构建 `stt-cpu` 生产镜像，在禁用网络的容器中加载 Torch / torchaudio `2.11.0+cpu`、Whisper、FunASR、ModelScope、Silero VAD 和 DashScope，确认版本配套且可导入。此检查不下载模型、不执行语音推理；CUDA 仍须在 GPU 环境验收。

上线验收至少记录以下项目，固定源码提交、模型版本、音频长度和输入设备后再比较：

| 范围 | 记录内容 |
|---|---|
| 启动 | 宿主机与 Docker 配额、镜像大小、可用磁盘、冷启动与热启动时间 |
| 模型 | 引擎、模型、量化方式、下载大小、加载耗时、峰值内存/显存、音频长度与处理耗时 |
| 会议 | 明确人数和时长，分别验证聊天、麦克风、摄像头、共享、录音及会后任务；记录断线与失败率 |
| 存储 | 上传大小、速率、CORS、签名下载、对象保留和失败重试；数据库和对象备份分别验证 |
| 稳定性 | 长会、弱网、客户端退出与重入、任务积压、磁盘增长，以及备份恢复 |

容量提高前先找出瓶颈。不要把健康接口的高吞吐写成多人会议并发能力，也不要依据机器核心数直接提高 STT 并发。生产巡检、备份与恢复见[运维指南](../server/OPERATIONS.md)，当前平台边界见[功能状态](feature-status.md)。
